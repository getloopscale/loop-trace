## [Unreleased]

### Added
- Roadmap amended (`ROADMAP-edge-integration.md`): **M137 — Publication gates** (`/roadmap-feature cicd-publish-gates`). Comparing this pipeline against theo-memory's — the model the umbrella `CLAUDE.md` declares for the workspace — found a hole here that the model does not have: `publish.yml`'s `image` job declares **no `needs:`**, so `ci`, `integration` and `security-sast` run *in parallel with* the build rather than before it. A failing gate does not stop the push, and the `:develop` tag the dev host reconciles can point at an artifact from a rejected commit. Verbatim the defect theo-rag closed in `#160`, where theo-memory's DevOps audit measured it: **11 of 134 pushes (8.2%)** published an image with the Postgres suite red on the same commit, the gate finishing *after* the publish. M137 adopts theo-memory's shape — `needs: [gate-ci, gate-contract, guard-release-on-main]`, `workflow_call` on the two gates (neither has it today, so neither can be a gate), a tag-must-be-in-`main` guard before `:latest`, and `paths-ignore` on `ci.yml`. The gate is pinned by a test rather than by inspection, so a later edit cannot silently reopen it. **Deliberately excluded, and split into M138:** migrating the deploy from PUSH (SSH from CI, `DEV_SSH_KEY` + `DEV_HOST`) to PULL — it touches theo-workspace, removes secrets from this repo, and a milestone whose DoD depends on a neighbouring repo cannot close on its own. That one matters here specifically: this repo is Apache-2.0 and headed for publication.
- CD playbook documented for this capability at `docs/cd-pipeline.md` — what differs from the reference and why.

- CD pipeline complete (playbook Phases 3-6): integration + SAST lanes on the repo's own self-hosted runner, and `publish.yml` — a develop push builds, publishes to GHCR and deploys to dev behind a version gate and a health gate; a `v*` tag builds, signs, and never touches dev.


- CD pipeline groundwork (playbook Phases 1-2): `docker-compose.deploy.yml` runs the API from the GHCR image, and `scripts/deploy-dev.sh` gates a deploy on two assertions — the running image's OCI revision label equals the deployed commit, and both liveness and readiness are green.
- `GET /v1/version` now reports `{name, version, git_sha, built_at, node}` so "what is live?" has an answer a human can read.

## [0.62.0] - 2026-07-21

### Added

- `/v1/monitors*` — the canonical path for what was `/v1/guards*` (M136). Same behaviour; the name no longer promises request-path enforcement theo-lens does not do.

### Changed

- README documents Monitors explicitly against guardrails: a Monitor observes after the fact and never blocks; a `guardrail` is inline in **your** application and is recorded by Theo Lens only as a span kind. The old name promised enforcement that was never implemented and, by design, never will be.

### Deprecated

- `/v1/guards*` — kept as an alias mounted on the same handlers, removed in the release after this one. Migrate to `/v1/monitors*`.
- The `guards` key on the monitor-list response, and `guardExists` on the breach-window response. Both are now emitted alongside their canonical twins (`monitors`, `monitorExists`) and hold the same value; both are removed with the path alias. The old names were kept because dropping them would break consumers *through the compatibility alias itself* — an alias that preserves the path but changes the payload is a silent break wearing a compatibility badge.

## [0.61.0] - 2026-07-21

### Added

- Guard breaches now notify (M135). A guard threshold used to be computed only when a human opened the screen; a guard-backed alert rule (`metric: guard_breach`) is evaluated on the existing 60s cadence and fires through the existing anti-storm state machine and webhook path.
- `GET /v1/guards/:id/breach-window` — per-guard breach counts over a window. It distinguishes three states the previous read-side query could not: a measured zero (`hasData: true, breachCount: 0`), an empty window (`hasData: false`), and a guard that does not exist in your workspace (`guardExists: false`). Collapsing the first two is theo-cloud#247; collapsing the last two leaves an alert rule armed against something that is gone.


### Fixed

- A failed heartbeat during auto-evaluation is now logged and counted instead of discarded. A missed refresh is not fatal to the running job, but it is the precondition for the failure the heartbeat exists to prevent — the claim goes stale, another worker takes over, and the trace is judged twice. Swallowing it left that invisible.

## [0.60.0] - 2026-07-21

### Added

- Automatic evaluation of new traces (M134): an evaluator marked auto now scores qualifying newly-ingested traces without an operator. Opt-in per evaluator (`autoEnabled`, default off) and per deployment (`THEOLENS_AUTO_EVAL=1`), with a sampling rate and a trace filter to bound cost. Scoring never touches the ingest path — the enqueue is fire-and-forget and its failures are counted, so an eval-side outage can never fail or slow an ingest.
- Auto-evaluation groundwork (M134 T1.1): `evaluators` gains `auto_enabled` (default OFF, so upgrading starts no judge spend), `sampling` and `filter`; new `eval_jobs` table is the claim-a-row work queue (ADR D1 — chosen over Redis-backed queues because it needs no new infrastructure and cannot lose accepted work). Dedup is a DB unique constraint rather than application logic, and `eval_jobs` joins the retention cascade so it neither grows without bound nor leaves rows that outlive their traces.
- Roadmap amended (`ROADMAP-edge-integration.md`): **M133 backfilled as `[x]`** (async evaluator runs — already delivered, the milestone id was only ever a code/CHANGELOG label), plus three new milestones from the 2026-07-21 deep research into how the field implements evaluations vs guardrails (`/roadmap-feature`). **M134 — Automatic evaluation of new traces (target filter + sampling + event-driven worker)**: today `runEvaluator` is the *only* `writeVerdict` caller, the ingest path never scores and the sweep is OFF by default, so Guards — a read-side threshold *over verdicts* — monitor a stream nobody produces; Langfuse auto-scores new traces event-driven (`worker/.../IngestionService/index.ts:705-735`, `evalService.ts:180,619-629`, `schema.prisma:1051-1078`) while Phoenix has no auto-eval at all, making this the decisive gap. **M135 — Guard breaches notify**: wire eval thresholds into the *existing* M53 alert/webhook path (comparator + anti-storm state machine), mirroring Langfuse Monitors (severity + dedup + `WEBHOOK|SLACK`, never blocking); depends hard on M134. **M136 — Rename Guards → Monitors**: both references reserve `GUARDRAIL` for a span kind labelling the blocker in the *user's own app* (Phoenix: *"Phoenix doesn't block requests — your app does"*), and Langfuse names the equivalent feature Monitors — the current name over-promises enforcement. Also adds **"inline/blocking guardrails inside theo-lens"** to the roadmap's explicit out-of-scope list (an observability data plane is not a policy-enforcement proxy; enforcement belongs in the app/gateway and theo-lens observes it as a `guardrail` span).

### Changed

- **Evaluator runs are now async (M133) — no more 502 on an `llm_judge` run.** `POST /v1/evaluators/:id/run` scored every selected span *synchronously inside the HTTP request*; for an `llm_judge` evaluator that fanned out one provider round-trip per span, **serially**, so a run over ~100 spans exceeded the edge timeout and returned `502` with NO verdict written (a silent failure). Two bottlenecks removed: (1) the run is **async** — the route registers a job and returns **`202`** with a queued job immediately (the POST no longer blocks on the fan-out, so it scales with N); the client polls the new **`GET /v1/evaluator-run-jobs/:id`** for `status` + `scored/total` progress. (2) the fan-out is now **bounded-concurrent** (`RUN_CONCURRENCY = 6`) instead of serial, so wall-clock is ~N/6 provider round-trips, not N — without an unbounded `Promise.all` that would flood the provider. Rule evaluators stay serial (CPU, instant). The job registry is **in-memory** (theo-lens is single-process); a durable, multi-instance store is the documented follow-up. `RunResult` gains `total` (the progress denominator). Engine tests cover bounded-concurrency scoring + progress; api tests cover 202-then-poll-completed + workspace-scoped 404.

### Fixed

- Discovery citation gate was inert: both `discover-confidence` and `discover-plan-confidence` matched only `.claude/knowledge-base/references/...` while this repo stores reference clones at `knowledge-base/references/...`. Across the 26 existing blueprints this produced 67 false "fabricated" citations and silently scored 16 others as having no citations at all. Both checkers now accept either root and resolve against both; the sweep is 90 citations, 90 verified, 0 fabricated.
- Auto-evaluation review hardening (M134): seven defects found in pre-merge review, four of which cost money or lose work silently. Sampling was decided AFTER the job row was written, leaving a committed window in which a rejected job could still be claimed and run; the trace filter was evaluated against a whole OTLP batch, so one matching trace pulled every other trace in that batch into evaluation; a job outliving the stale-claim window was reclaimed and re-run while still in flight; and jobs whose evaluator had been deleted were counted as completed evaluations, inflating the very metric the feature's success is measured by. Also fixed: enabling auto-evaluation on an *existing* evaluator was impossible through the API (the update path silently dropped the new fields), and a continuously-streaming trace could postpone its own evaluation indefinitely.
- Auto-evaluation claim query no longer scans the whole job table: the index it depended on could never be used, because the query asked which statuses to *exclude* rather than which to *include*. Measured on 200k rows, the sweep went from 23.8 ms (sequential scan plus sort) to 0.083 ms (indexed).

## [0.59.0] - 2026-07-21

### Changed
- **M64 experiment runs now score `llm_judge` evaluators (real quality A/B).** The experiment engine (`experiment-engine.ts`) previously scored only `rule` evaluators over the replayed output (the M64 D2 rule-only slice), so an A/B experiment never surfaced a real quality signal — only pass/fail rule verdicts. The engine now takes an optional injected `judge` (DIP): when present, `llm_judge` evaluators ALSO score the replayed output via the SAME provider judge reused by copilot/replay (D1), so an experiment's mean-score and compare deltas reflect real LLM-judged quality. Fail semantics stay layered — a judge error fails open per-evaluator (that score drops, the run stays `completed`), while a replay error still fails the item (`partial`). With no judge injected the engine stays rule-only (backward compatible). Wired end-to-end: `ExperimentApiDeps.judge` → composition root passes the pinned judge. Engine tests 8/8 (llm_judge scored-with-judge / skipped-without-judge / judge-error fail-open).

### Fixed
- **Boot no longer crashes resolving migrations.** `migrateLatest` runs from `db/observability/`, but the migrations live one level up at `db/migrations`; the module resolved `./migrations` (a nonexistent `db/observability/migrations`), so a fresh boot failed with `Can't find meta/_journal.json` (the `main` branch only "worked" because its stale `dist` still carried the old module at `db/`). Now resolves `../migrations` and exports `MIGRATIONS_DIR` for a regression test that asserts the resolved path ends at `infrastructure/db/migrations` and that `meta/_journal.json` exists on disk.

## [0.16.0] - 2026-06-23

### Added
- Live auto-refresh: the executions list, dashboards, sessions, metrics, and tool/cost analytics views refresh themselves on a configurable interval (Off / 5s / 10s / 30s / 1m, default Off) via a toolbar control with an "updated Xs ago" freshness indicator (announced to assistive tech), so an operator watching agents run live (e.g. a Claude Code session ingesting via M15) never reloads the page. Polling pauses while the browser tab is hidden and the open trace view is never auto-refreshed. Built on the existing react-query layer (`refetchInterval`) — zero new dependency, no backend change (M16)

## [0.15.0] - 2026-06-23

### Added
- Claude Code integration: point Claude Code's OpenTelemetry trace export at Theo Lens (helper `scripts/theo-instrument-claude.sh`) and its agent sessions appear as first-class executions — model, tokens, cost, input, and session grouping all populate. Built on an extensible **agent-adapter** seam (selected by `service.name`) so other external agents (Codex, …) integrate by adding one adapter, with zero change to existing traces. Verified by dogfooding a real Claude Code session into Theo Lens (M15)

## [0.14.0] - 2026-06-22

### Added
- Tags: attach free-form tags to a trace (`POST`/`DELETE`/`GET /v1/traces/:id/tags`) and filter the executions list by tag (`GET /v1/traces?tag=`). The trace view gains an add/remove-tags panel and the list toolbar a tag filter. Tags are a lightweight grouping orthogonal to sessions (a trace can have both), stored in a side table with no change to spans/traces; adding a tag is idempotent and tagging a non-existent trace returns 404 (M14)

## [0.13.0] - 2026-06-22

### Added
- Sessions: `GET /v1/sessions` (newest-first) + `GET /v1/sessions/:id` group related traces (a multi-turn conversation / workflow sharing a `session.id` / `gen_ai.conversation.id`) and show session-scoped metrics — total cost, tokens, latency p50/p95, error rate — plus the member trace list. A `/sessions` view + a trace→session link render these with loading/error/empty states; traces without a session id stay standalone and are never grouped into a fabricated session (M13)

## [0.12.0] - 2026-06-22

### Added
- Rich span detail: the span detail panel now renders distinct Input / Output / Events / Attributes / Status sections — input/output as XSS-safe markdown, events and attributes as collapsible JSON with copy-to-clipboard — instead of one raw JSON dump. The SDK gains `setInput`/`setOutput` (emitting `input.value`/`output.value`), ingest captures those plus OTLP span events (bounded to 8 KiB text / 50 events to avoid storing unbounded blobs), and spans without the new fields still render gracefully (M12)

## [0.11.0] - 2026-06-22

### Added
- Observability dashboards: a `/dashboards` view and `GET /v1/metrics/observability?range=1h|24h|7d|30d` show time-series traffic + error rate, latency percentiles (p50/p75/p95/p99), and tokens + cost broken down by model over a selectable time range — each metric as an accessible data table plus a lightweight inline-SVG sparkline (no charting dependency added) (M11)

## [0.10.0] - 2026-06-22

### Added
- Trace waterfall: the span tree now shows a time-aligned bar per span (proportional offset + duration) so you can see where a trace spent its time, plus a span-kind icon (LLM / tool / retriever / chain) and a trace-level "contains an error" indicator that surfaces a failure anywhere in the tree (M10)

## [0.9.0] - 2026-06-22

### Added
- V1 ship gate: a single automated end-to-end test walks the full journey from a clean `docker compose up` — start the stack, instrument and run the example agent, ingest spans, see the execution tree, walk the session replay, and check cost + tool analytics — so V1 readiness is a binary, reproducible check (`pnpm test:e2e`) (M8)
- North-star metrics in Lens itself: a `/metrics` view and `GET /v1/metrics/north-star` show traces ingested per day and replay sessions opened per week (M8)
- Executions list search: `GET /v1/traces` accepts filter (status, model, time range) + sort (recency / latency / tokens / cost) so you can find a specific execution instead of scrolling a flat list; each execution now shows an ok/error status (a trace is error if any of its spans errored); the filtered list exports to CSV/JSON (M9)

## [0.8.0] - 2026-06-21

### Added
- One-command stack: `docker compose up` now serves the Trace Explorer UI from the API at the same origin (http://localhost:4318) and applies database migrations on boot, so a clean checkout is ready to receive spans and view them with no manual migration or second service (M7)

## [0.7.0] - 2026-06-21

### Added
- Tool analytics: tool-call spans are extracted to a typed indexed `tool_name` at ingest; `GET /v1/analytics/tools` ranks tools by call count / latency p50/p95 / error rate over a recent window, and `GET /v1/analytics/tools/:name/traces` drills down to the executions that called a tool — rendered as a sortable ranking view + drill-down in the UI. Tool error rate counts both numeric and textual ERROR span status consistently, and latency ignores clock-skewed negative durations (M6)

## [0.6.0] - 2026-06-20

### Added
- Cost analytics: per-execution USD cost is computed from span token attributes via a configurable per-model price table and stored at ingest; `GET /v1/traces/:id/cost` and `GET /v1/analytics/cost?period=day|week` expose per-trace and day/week cost, rendered as a total in the trace detail and a period view in the UI (M5)

## [0.5.0] - 2026-06-20

## [0.2.0] - 2026-06-20

### Added
- OTLP protobuf ingestion: `POST /v1/traces` now accepts `application/x-protobuf` (and gzip) in addition to JSON (M1)
- Trace data model: `sessions` / `traces` / `spans` tables; traces and sessions are aggregates recomputed from spans (M1)
- Trace tree reconstruction: `GET /v1/traces/:traceId` returns the nested span tree assembled by parent/child relationships (M1)
- GenAI attribute extraction: model, provider, and input/output token counts are extracted from spans into typed columns (M1)


### Changed
- Trace/span ids are normalized to canonical lowercase hex on ingestion, so the same trace is consistent across SDK encoders (M1)


### Fixed
- Trace tree reconstruction is robust to malformed input: cyclic parent links are broken so the trace view never fails to render, and traces with multiple root spans return a single tree (M1)
- Concurrent ingestion of the same trace computes exact, stable token/cost totals (no double-counting on retried batches, no lost updates under load) (M1)
